# 鸿蒙被控端平台能力探针

日期：2026-10-18，初轮本地测试约10:09—10:27（中国时间），后续云端检查记录于下文。用户批准“先验证平台能力，再实现被控端”。本轮使用独立临时包，不覆盖现有UU-REA，不接入UU账号或被控协议。

结论：**PARTIAL。全局鼠标和跨应用键盘已实测通过；当前API23模拟器的原始屏幕取帧、NDK H.264编码未通过。后续复核找到官方模拟器媒体能力限制，targetSdkVersion降至23也未改变结果，应转向鸿蒙电脑真机重测。官方Mac / Windows UU控制鸿蒙仍未实现。后续用户将反向被控暂缓，最新主控范围见[本地Mac验收](2026-10-20-本地Mac稳定性与电脑分组.md)。** 不能将授权成功、启动回调或输入接口返回0表述为远控成功。

## 环境与范围

运行端为现有UU_REA_PC_API23、HarmonyOS6.1.0.115/API23、PC/2in1，3120×2080。编译SDK26，兼容API23。探针包com.luke.uureaprobe通过NAPI调用公开NDK；独立输入验收板com.luke.uureaprobe.target无网络、注入或屏幕采集功能。

原计划使用系统计算器，但该模拟器未安装计算器，系统设置也没有可用搜索框。因此鼠标以系统设置切换页面验收；键盘以另一个应用的离线算式输入和实际结果验收。两项均跨越应用边界，不把探针自身文本变化算全局输入成功。

## 结论边界与下一步

系统授权和跨应用输入说明普通应用的API23用户授权NDK路线确实可用，没有使用系统签名、CONTROL_DEVICE、辅助功能绕路或修改系统权限。

零帧发生在图片转换/映射之前；新旧回调都未收到视频数据，不能归因于PPM转换失败。YUV初始化拒绝是另一个已记录分支。初轮尚未找到明确的模拟器规格依据；后续复核已找到官方明确限制，见下一节。这不能推广为鸿蒙真机不可被控。

NDK H.264创建失败发生在尺寸/码率配置之前，因此不是本轮1280×720/15fps参数配置失败的证据。这里只确认当前镜像未暴露该编码器能力，没有验证另带软件编码器或ArkWeb发送编码的替代路线。

被控端完整媒体链路尚未具备验证条件。下一步先在鸿蒙电脑真机验证有效取帧与可解码的H.264码流；通过后再实现UU被控注册/上线/接入监听、SDP应答、视频发送与输入解码，最终由Windows官方UU验收。当前没有添加“可被远控”的占位开关或伪造在线设备。
